## 1. 参考对象拆解

### 1.1 PCL 的启动逻辑

PCL 的启动体验有四个可拆解的设计点：

| 设计点 | PCL 的做法 | 价值 |
|---|---|---|
| 启动是首要动作 | 首页即"选版本 + 点启动"，其余功能是二级页面 | 打开就想启动，路径最短 |
| 启动前预检 | Java 缺失、内存不足、版本文件残缺都在启动前拦截，并直接给修复入口 | 不让用户拿崩溃日志猜原因 |
| 启动状态机 | 启动中 → 运行中 → 已退出，按钮文案与可用性同步变化 | 用户始终知道处于什么状态 |
| 实例切换无需重启 | 版本下拉切换后直接作用于下一次启动 | 降低心理负担 |

SMMS 已具备第 1、3 点（顶栏常驻启动区、状态联动），第 2 点是最大缺口。

### 1.2 Minecraft 整合包的文件模型

整合包的本质不是"一堆 mod 文件"，而是**清单驱动**：

```
.minecraft/versions/1.20.1-forge/
├─ 1.20.1-forge.json      # 版本清单：依赖 minecraft 1.20.1 + forge 47.2.0
├─ 1.20.1-forge.jar
└─ mods/                  # 版本隔离时落在实例内
   ├─ jei.jar
   └─ ...
```

Modrinth 格式的清单片段：

```json
{
  "formatVersion": 1,
  "game": "minecraft",
  "versionId": "1.0.0",
  "dependencies": { "minecraft": "1.20.1", "forge": "47.2.0" },
  "files": [
    {
      "path": "mods/jei.jar",
      "hashes": { "sha1": "..." },
      "downloads": ["https://cdn.modrinth.com/..."],
      "fileSize": 1234567
    }
  ]
}
```

三个关键能力由此而来：

1. **校验**：清单有 hash 和依赖约束，能判断实例是否完整
2. **复现**：换台机器按清单重建同样的环境
3. **增量**：只比对差异，不重复下载

**当前 SMMS 的配置档只是"另一个 Mods 目录"，没有清单。** 这直接导致：无法校验完整性、无法检测缺失依赖、无法导出分享、无法比对差异。这是本次要补的核心，而不是目录结构调整。

### 1.3 共同点

PCL 与整合包的交集是：**启动前一定知道"要启动什么"，并且能证明它是完整的。**

## 2. 星露谷的能力边界（必须先说清）

这是整个设计最关键的一节。很多在 MC 里成立的做法，在星露谷做不到，原因不是实现难度，而是游戏本身没提供对应的开关。

| 隔离维度 | Minecraft | 星露谷 | 结论 |
|---|---|---|---|
| 模组目录 | `versions/<id>/mods` | `--mods-path` 参数 | ✅ 可做 |
| 工作目录 | `--gameDir` 可指向任意路径 | 无此参数，固定为 exe 所在目录 | ❌ 不可做 |
| 配置文件 | 随实例走 | `smapi-internal/config.json` 全游戏一份 | ❌ 不可做 |
| 存档 | 随实例走（saves 在实例内） | `%AppData%\StardewValley\Saves` 全局唯一 | ❌ 不可做，除非改符号链接 |
| 游戏版本 | 多版本共存 | 一个目录一份游戏 | ⚠️ 需复制整个游戏目录 |
| 加载器版本 | 多版本共存 | 一个目录一份 SMAPI | ⚠️ 同上 |

**根本原因**：Minecraft 启动器可以把整个工作目录指到任何地方（`--gameDir`），所以"实例"是天然的一等概念。星露谷的 SMAPI 只开放了 `--mods-path` 一个口子，其余路径全部由游戏和 exe 位置决定。

**因此**：SMMS 的"配置档"等价于 MC 整合包实例的**模组子集**，不是完整实例。这个边界必须写进产品文案，否则用户会以为切换配置档能连存档一起换。

如果要突破这个限制，唯一路径是**完整实例模式**：复制整个游戏目录（约 1–2 GB）到 `_smms/instances/<id>/`，启动时直接运行该副本的 `StardewModdingAPI.exe`。代价是磁盘占用线性增长，收益是存档、配置、SMAPI 版本全部独立。

这个取舍需要产品决策，见第 7 节。

## 3. SMMS 实例模型

### 3.1 隔离模型（已决策：由用户按配置档自定义）

隔离不是全局开关，而是**每个配置档自己的属性**。用两个独立维度表达，比三级枚举更灵活：

```csharp
public sealed record ProfileIsolation
{
    /// <summary>复制完整游戏目录，实例自带游戏本体与 SMAPI。</summary>
    public bool IsolateGameInstance { get; init; }

    /// <summary>把存档复制到实例内，启动前切换链接。</summary>
    public bool IsolateSaves { get; init; }
}
```

三种预设由这两个开关组合而成：

| 预设 | 隔离游戏本体 | 隔离存档 | 磁盘成本 | 适用场景 |
|---|---|---|---|---|
| 仅模组（默认） | 否 | 否 | 模组总大小 | 单人 / 联机切换 |
| 模组 + 存档 | 否 | 是 | + 存档大小 | 多存档流派 |
| 完整实例 | 是 | 可选 | 1–2 GB / 档 | 多游戏版本并行 |

**智能默认（按游戏版本判定）**

配置档在 `requirements.gameVersion` 里记录创建时的游戏版本。启动时比对当前游戏版本：

- **版本一致** → 默认仅模组隔离。共享同一份游戏本体和 SMAPI，最省磁盘
- **版本不同** → 提示必须使用完整实例。因为不同游戏版本不能共用一份本体，共用必然导致模组或 SMAPI 行为错乱

这条规则的意义是：普通玩家永远遇到的都是"版本一致"，无感；只有当玩家刻意保留旧版本游戏时才触发完整实例，磁盘代价由他自己选择。

**存档隔离的实现约束**

存档实际位于 `%AppData%\StardewValley\Saves`，游戏不接受参数改变。因此只能：

1. 切换配置档时，把真实 Saves 目录移走，用 junction 指向实例内的 Saves
2. 游戏运行期间**禁止**切换——正在写入的存档被移走会截断

这一点必须在 UI 上硬性拦截，不能只靠提示。

**外部引用（已有独立备份）**

玩家常常先手动复制整个游戏目录做备份，这些目录本身就是一个完整实例。要求他们重新用 SMMS 复制一遍纯属浪费，因此配置档支持**直接引用**已存在的目录：

| 来源 | 目录位置 | 创建成本 | SMMS 是否拥有 |
|---|---|---|---|
| 主安装 | 游戏原始位置 | — | 否，共用 |
| 自建副本 | `<profileRoot>/instance` | 复制 1–2 GB，数十秒 | 是，删除配置档时一并删除 |
| 外部引用 | 玩家自选路径 | 秒级，只建清单 | **否，只解绑不删除** |

三者对上层完全等价：都会被解析成一个「配置档自己的游戏根目录」，扫描、启用禁用、启动、预检一律只认这个路径。差异只体现在创建方式和删除行为上。

约束：

- 同一目录不允许被两个配置档同时引用，否则改一处会波及另一处
- 外部目录被手动删除或移动后，`ResolveForProfile` 返回 null，启动预检报「完整实例不存在」，不会静默回落到主安装
- 删除外部引用型配置档时只删 `<profileRoot>`（存清单用），外部游戏目录一个文件都不动

### 3.2 目录结构

```
<游戏目录>/
├─ Mods/                          内置默认档（SMAPI 原生目录，不纳入清单管理）
├─ StardewModdingAPI.exe
└─ _smms/
   ├─ profiles/
   │  └─ <profileId>/
   │     ├─ profile.json          实例清单（核心）
   │     ├─ Mods/                 该档的模组目录
   │     └─ _disabled/            禁用区，在 Mods 之外，SMAPI 不会扫描
   ├─ library/                    中央模组库（Phase 2，硬链接共享用）
   ├─ snapshots/                  启动/更新前的快照
   └─ smms.db                     索引与缓存
```

`_disabled` 放在 `Mods` 之外而不是内部，是因为 SMAPI 会扫描 `Mods` 下所有子目录找 `manifest.json`，放在里面会被误加载。

### 3.3 profile.json 规格

```json
{
  "schemaVersion": 1,
  "id": "p20261030-abc123",
  "name": "轻量联机",
  "createdAt": "2026-10-30T13:00:00+08:00",
  "updatedAt": "2026-10-30T13:20:00+08:00",
  "isolation": "mods",
  "requirements": {
    "gameVersion": "1.6.15",
    "smapiVersion": "4.5.1"
  },
  "mods": [
    {
      "uniqueId": "Pathoschild.ContentPatcher",
      "name": "Content Patcher",
      "version": "2.4.0",
      "nexusId": "1915",
      "folder": "ContentPatcher",
      "enabled": true,
      "manifestSha256": "9f2c...",
      "isContentPack": false
    }
  ]
}
```

设计要点：

- **以 `uniqueId` 为主键**，不以文件名为准。星露谷模组可以随意改文件夹名，但 `UniqueID` 是稳定标识
- `requirements` 记录创建时的环境版本，导入到别的机器时用来提示差异
- `manifestSha256` 用于完整性校验。不记录模组文件本身的 hash，因为单个模组可能是几十个文件，逐文件 hash 成本高且收益低——manifest 变了基本等于版本变了
- `enabled` 是逻辑状态，实际位置在 `Mods/` 或 `_disabled/`，两者需保持一致（启动扫描时自动校正）

## 4. 启动流程（PCL 式预检）

```
用户点「启动游戏」
        │
        ▼
┌───────────────────────────────┐
│ 预检（按顺序短路）              │
│ 1. 游戏目录有效？               │  ERROR
│ 2. SMAPI 模式？ → 已安装且版本满足 │  ERROR
│ 3. 实例 Mods 目录存在？          │  ERROR
│ 4. 是否有游戏进程已在运行？       │  ERROR
│ 5. 扫描模组：解析失败的 manifest  │  WARN
│ 6. MinimumApiVersion 是否被满足  │  ERROR
│ 7. 必需依赖是否齐全              │  WARN
│ 8. 实例 requirements 与实机差异   │  WARN
└───────────────────────────────┘
        │
   ┌────┴────┐
 有 ERROR   全部通过
   │          │
   ▼          ▼
中止并展示   构造 LaunchPlan
问题清单     启动 → Running
每项带修复入口
```

**关键设计**：预检结果不是一句"启动失败"，而是一张问题清单，每项包含"哪个模组/哪个文件 + 什么问题 + 怎么修"。

例如：

```
× SMAPI 版本不足
  「Stardew Valley Expanded」要求 SMAPI ≥ 4.6.0，当前 4.5.1
  [升级 SMAPI]  [忽略并继续]

! 缺少必需依赖
  「Ridgeside Village」依赖「Content Patcher」≥ 2.0.0，未安装
  [去 Nexus 下载]
```

这比让玩家看 SMAPI 控制台的红色文字有用得多，也是 PCL 体验优势的来源。

## 5. 导入 / 导出（整合包式）

### 5.1 导出

```
<packName>.smms.zip
├─ profile.json      实例清单
├─ mods/             可选
└─ README.md         自动生成：版本要求、模组清单、来源链接
```

两种模式：

| 模式 | 内容 | 体积 | 合规 |
|---|---|---|---|
| 仅清单（默认） | 只有 profile.json | KB 级 | ✅ 无版权问题 |
| 含模组 | 打包 Mods 目录 | 数百 MB | ⚠️ 分发他人模组需作者授权 |

**默认且推荐只导出清单。** 模组版权属于作者，打包分发属于二次分发，风险由使用者承担，产品不该默认引导。

### 5.2 导入

```
读 profile.json
  → 校验 schemaVersion
  → 比对 requirements 与实机（游戏/SMAPI 版本）
  → 按 uniqueId 匹配本地已安装模组
      ├─ 版本一致 → 直接复用
      ├─ 版本不同 → 标记待更新
      └─ 缺失     → 生成待获取清单
  → 创建实例目录，放置能匹配的模组
  → 展示"还差 N 个模组"，每个带 Nexus 链接
```

**不承诺自动下载**。免费账号受 Nexus 政策限制（见 ADR-001），强行做全自动会在多数用户那里失败。给链接列表 + 手动导入，是能兑现的体验。

## 6. 与现有实现的差异

| 项 | 当前 | 目标 |
|---|---|---|
| 配置档 | 仅一个 Mods 目录 + settings.json 里一行记录 | 目录 + profile.json 自描述清单 |
| 启动 | 直接构造 LaunchPlan 执行 | 先预检，通过后执行 |
| 完整性 | 无 | 按清单校验缺失/版本不符 |
| 分享 | 无 | 导出/导入清单 |
| 禁用模组 | 未实现 | 移到 `_disabled`，清单记录状态 |

## 7. 决策记录

### 7.1 隔离层级（已决策）

三个级别全部实现，由用户按配置档选择。默认策略：游戏版本一致时仅模组隔离，版本不同时强制完整实例。存档隔离为独立开关。

### 7.2 导出范围（已决策）

默认只导清单，用户可勾选「一并打包模组文件」。勾选时给出明确提示：分发他人模组需取得作者授权，风险由使用者承担。

### 7.3 预检严格程度（已决策）

ERROR 级**阻断**，但保留出口：弹窗列出全部问题与可能后果，用户可选「取消启动」或「仍然启动」。

不静默放行，是因为模组不兼容的表现是游戏闪退，玩家很难自行关联到「某个模组要求更高的 SMAPI 版本」。
