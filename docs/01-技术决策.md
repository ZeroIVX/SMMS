# SMMS 技术决策文档

> Stardew valley Mods Management System
> 版本：v0.1（决策基线）
> 状态：已确认，可进入实施阶段
> 日期：2026-10-29

---

## 1. 项目定位

SMMS 是一款面向《星露谷物语》（Stardew Valley）玩家的 Windows 桌面模组管理器。

它要解决的核心痛点：**SMAPI 与模组生态的版本联动，目前全靠手动**。SMAPI 一更新，模组可能集体失效；模组要更新，又得逐个去 Nexus 翻页面下载、解压、覆盖。整个过程没有统一的版本视图，也无法回退。

SMMS 的目标是把这套流程收敛到"打开管理器 → 看到全部版本状态 → 执行升级 → 出问题一键回滚"。

### 明确不做的事

- 不做模组发布平台，不做社区功能
- 不修改游戏本体文件（除 SMAPI 安装所需的官方安装流程）
- 不替代 Nexus，只做客户端侧的组织与自动化
- 不承诺绕过 Nexus 的下载权限限制

## 2. 已确认的硬约束

以下四条是经过查证的事实，构成了整个架构的地基。它们的引用来源写在括号里，后续改架构前必须先复核。

### 2.1 SMAPI 可以静默安装

SMAPI 官方安装器支持三个参数（来源：SMAPI 技术文档 `docs/technical/smapi.md`）：

| 参数 | 作用 |
|---|---|
| `--install` | 预选安装动作，跳过交互询问 |
| `--game-path "路径"` | 指定游戏目录，跳过自动探测 |
| `--no-prompt` | 不等待用户输入，无法继续时直接失败 |

因此"SMAPI 升级"是完整可自动化的流程：下载官方 installer zip → 解压 → 调用安装器 → 读取退出码。

### 2.2 模组更新检测不需要 Nexus 账号

SMAPI 官方提供批量更新检查接口（来源：SMAPI 技术文档 `docs/technical/web.md`）：

```
POST https://smapi.io/api/v4.0.0/mods
```

请求体给出每个模组的 `id`、`updateKeys`、`installedVersion`、`isBroken`，以及全局的 `apiVersion`、`gameVersion`、`platform`。响应返回 `suggestedUpdate.version` 与 `suggestedUpdate.url`。

关键点：**该接口公开、无需 API Key、支持批量、带官方更新建议规则**（例如稳定版用户不会被推荐预发布版）。它还内部交叉引用了 Wiki 兼容性列表、CurseForge、ModDrop，所以能拿到 `compatibilityStatus` 和 `brokeIn`。

这意味着：**即使使用者没有任何 Nexus 账号，SMMS 依然能完整提供"检测更新 + 判断兼容性"能力**。只有"下载"这一环受账号等级影响。

### 2.3 Nexus 下载受账号等级限制

Nexus API 的 `download_link.json` 直链**只对 Premium 会员返回**（来源：Nexus API 政策、多个第三方管理器实现文档）。

免费账号必须走 `nxm://` 协议：用户在网页点击 "Mod Manager Download"，浏览器唤起 `nxm://stardewvalley/mods/<id>/files/<fileId>?key=<key>&expires=<ts>`，客户端解析出 `key` 与 `expires` 后再调 API 换直链。

这是政策限制，不可绕过，只能通过产品设计降低门槛。详见第 5 章 ADR-001。

### 2.4 SMAPI 原生支持多模组目录

SMAPI 支持 `--mods-path` 参数指定非默认的 Mods 目录，可以是相对路径也可以是绝对路径（来源：SMAPI 技术文档 + 官方玩家指南）。

- Windows：`StardewModdingAPI.exe --mods-path "绝对路径"`
- Linux / macOS：改用环境变量 `SMAPI_MODS_PATH`

这是"版本隔离"（Profile）能力的实现基础，无需修改游戏或 SMAPI。

## 3. 技术栈

### 3.1 选型结论

| 层 | 选型 |
|---|---|
| 运行时 | .NET 10 (LTS)，目标框架 `net10.0` |
| 语言 | C# 14 |
| UI 框架 | Avalonia 12.x |
| MVVM | CommunityToolkit.Mvvm 8.x |
| 依赖注入 / 宿主 | Microsoft.Extensions.Hosting 10.x |
| 数据库 | SQLite（Microsoft.Data.Sqlite）+ Dapper |
| HTTP | HttpClient + Microsoft.Extensions.Http.Resilience（重试、限流、超时） |
| 归档解压 | SharpCompress（纯托管，支持 zip / 7z / rar / tar，无需外部 exe） |
| 日志 | Serilog（文件轮转 + 内存缓冲供 UI 实时查看） |
| 测试 | xUnit + FluentAssertions + NSubstitute |
| 打包分发 | Velopack |

版本号中的 `x` 表示以 NuGet 上的最新稳定版为准，不锁定小版本，避免文档过期。

### 3.2 为什么是这套

**.NET 而非 Node/Rust。** 这个项目九成的复杂度在后端：文件遍历、归档解压、进程生命周期、注册表、Steam 库路径解析、语义化版本比对。.NET 在这些方面全部是原生能力，不需要任何桥接层。Electron 要把每件事都过一遍 IPC，Tauri 要把每件事都写成 Rust command。

**Avalonia 而非 WPF。** 两者后端能力相同，差别在两处：一是 Avalonia 的样式系统是 CSS 思路（主题变量、选择器、明暗主题一套机制），做模组管理器这种"卡片 + 状态徽章 + 主题切换"的界面成本低得多；二是 Avalonia 有官方 VS Code 扩展，带 XAML 智能提示与预览，能在你惯用的编辑器里完成全部开发，WPF 做不到。

**只做 Windows，但按可移植方式写。** 平台相关能力全部收敛到四个接口后面（见 ADR-004），Windows 提供实现，其他平台注册一个显式"未支持"的实现并给出清晰提示。开源后其他开发者新增一个 `SMMS.Platform.Linux` 项目、在 DI 里换一行注册即可，不需要碰核心逻辑。

**SQLite 而非纯 JSON。** 需要存四类数据：已安装模组索引（含未安装到 Mods 的库文件）、快照记录、操作历史、smapi.io 元数据缓存。这些需要事务、按条件查询、增量更新，JSON 做起来会变成手写索引。Dapper 保持 SQL 直写，不引入 EF Core 的模型迁移负担。

## 4. 架构分层

采用简化版整洁架构，依赖方向单向向内：

```
SMMS.Desktop  ──▶  SMMS.UseCases  ──▶  SMMS.Core
                                              ▲
                                              │ 实现接口
SMMS.Infrastructure ─────────────────────────┘
        │
        ▼
   外部系统（游戏本体 / SMAPI / smapi.io / Nexus / GitHub）
```

| 项目 | 职责 | 依赖 |
|---|---|---|
| `SMMS.Core` | 领域模型、语义化版本、manifest 解析、端口接口定义。**不引用任何 IO 库** | 无 |
| `SMMS.UseCases` | 用例编排：安装、检查更新、批量升级、Profile 切换、快照回滚 | Core |
| `SMMS.Infrastructure` | 端口实现：文件系统、SQLite、HTTP 客户端、归档解压、平台适配 | Core |
| `SMMS.Desktop` | Avalonia UI（Views + ViewModels），DI 组装入口 | Application、Infrastructure |

`SMMS.Core` 不依赖 IO 是硬性要求，这决定了版本比对、兼容性判定、依赖解析这些最容易出错的逻辑可以脱离游戏环境做纯单元测试。

**关于 `SMMS.UseCases` 这个命名。** 这一层原本叫 `SMMS.Application`，但那样会形成命名空间 `SMMS.Application`，与 Avalonia 的 `Application` 类冲突——在 `SMMS.*` 命名空间下写 `Application.Current` 会被解析成命名空间而非类型，只能到处补全限定名。更名后从根上消除冲突，语义上也更准确：这一层承载的就是用例编排。

## 5. 关键设计决策（ADR）

### ADR-001：Nexus 三档账号的能力降级

**背景。** 使用者可能是 Premium 会员、免费账号、或者根本没有 Nexus 账号。产品不能只服务其中一种。

**决策。** 把"账号等级"建模为运行时探测的能力集合，而不是三套代码分支。

```csharp
public enum NexusCapability
{
    None,            // 无账号：只能读公开页面
    NxmProtocol,     // 免费账号：nxm:// 回调可换直链
    DirectApi        // Premium：API 直链下载
}

public interface INexusSession
{
    NexusCapability Capability { get; }
    Task<DownloadTicket> ResolveDownloadAsync(ModFileRef file, CancellationToken ct);
}
```

三个实现：`AnonymousNexusSession`、`FreeNexusSession`、`PremiumNexusSession`。由 `NexusSessionFactory` 在启动时依据本地令牌状态与 `users/validate.json` 的 `is_premium` 字段决定实例。

**三档账号的实际能力矩阵：**

| 能力 | 无账号 | 免费账号 | Premium |
|---|---|---|---|
| 扫描本地模组 | 是 | 是 | 是 |
| 检测模组更新 | 是（走 smapi.io） | 是 | 是 |
| 判断 SMAPI / 游戏兼容性 | 是 | 是 | 是 |
| 依赖缺失检测 | 是（解析 manifest 依赖） | 是 | 是 |
| 下载并安装更新 | 手动下载后拖入窗口 | 网页点一次，客户端接管 | 全自动队列 |
| 创建 / 切换 / 备份 | 是 | 是 | 是 |

**关键取舍。** 不做"假装全自动"的设计。UI 上必须诚实显示当前能力等级，并给出升级路径说明。一个"点了没反应"的按钮，比一个明确写着"需要 Premium 或手动下载"的按钮伤害大得多。

**免费账号的交互链路：**

```
用户在模组详情点「更新」
  → SMMS 打开浏览器到该模组的 Files 标签页
  → 用户点 "Mod Manager Download"
  → 浏览器唤起 nxm://，SMMS 已注册为处理器
  → SMMS 解析 key + expires，调 API 换直链
  → 自动下载、校验、解压、装进当前 Profile
```

用户只点了两次，后续全自动。这是免费账号能做到的最优体验。

### ADR-002：更新检测统一走 smapi.io

**决策。** 更新检测唯一数据源为 `smapi.io/api/v4.0.0/mods`，Nexus API 不作为检测来源。

**理由。**

1. 无需任何账号与 API Key，三档用户能力一致
2. 上游已经实现了完整的"建议更新"规则，包括预发布通道、`isBroken` 时的宽松策略、Wiki 兼容性状态。自己重新实现这套规则必然会与 SMAPI 的实际行为产生偏差，而偏差的后果是玩家照做之后游戏起不来
3. 支持批量，一次请求可覆盖数百个模组，避免踩 Nexus API 的速率限制
4. 返回 `metadata.nexusID`，可直接用于构造 Nexus 页面链接，反过来省掉了"模组 ID 映射"的维护工作

**实现要点。**

- 扫描 `<mods-path>/*/manifest.json`，读取 `UniqueID`、`Version`、`UpdateKeys`、`MinimumApiVersion`
- 以 `UniqueID` 为索引批量提交，`installedVersion` 传本地版本
- 提交本地 `apiVersion`（读 SMAPI 版本）与 `gameVersion`（读游戏程序集版本），让上游按实际环境给建议
- 结果按 `suggestedUpdate.version` 比对本地版本，仅做展示与排序，**不自行判断"哪个版本更好"**
- 响应缓存 30 分钟落 SQLite，离线时展示上次结果并标注时间

### ADR-003：版本隔离用 `--mods-path`，Profile 存放在游戏目录内

**决策。** 每个 Profile 是一套独立的 Mods 目录，启动时通过 `--mods-path` 指向它。

**目录布局：**

```
<游戏根目录>/
├─ Mods/                          SMAPI 默认目录（保留，不动）
├─ StardewModdingAPI.exe
├─ Stardew Valley.exe
└─ _smms/                         SMMS 工作区
   ├─ profiles/
   │  ├─ 纯净档/Mods/
   │  ├─ 拓展档/Mods/
   │  └─ 联机档/Mods/
   ├─ library/                    中央库：按 modId/version 存放归档
   ├─ snapshots/                  快照归档
   └─ smms.db                     SQLite
```

`_smms` 与 `Mods` 同级，不在 `Mods` 内部，因此不会被 SMAPI 的模组扫描误判。`_smms` 放在游戏目录内而非 `%AppData%`，是为了保证**与游戏同卷**，为后续硬链接共享做准备。

**边界说明（重要，避免误解）：**

- 隔离的是**模组集合**，不是 SMAPI 版本。一个游戏目录只能有一份 SMAPI，多版本 SMAPI 需要多份游戏副本，代价过高，不做
- 因此 SMAPI 升级会影响所有 Profile，升级前必须对全部 Profile 做快照
- Profile 之间可以引用同一份模组文件（Phase 2 用硬链接 / junction 实现），Phase 1 采用独立复制，简单可靠

### ADR-004：跨平台预留的四个接口

**决策。** 把所有平台相关行为收敛到 Core 定义的四个端口，Windows 提供实现，未知平台注册显式不支持实现。

```csharp
// 1. 定位游戏安装
public interface IGameLocator
{
    bool TryLocate(out GameInstallation installation);
}

// 2. 构造启动计划：参数与环境的差异都在这里消化
public interface IGameLauncher
{
    LaunchPlan BuildLaunchPlan(GameInstallation game, ModProfile profile);
}

public sealed record LaunchPlan(
    string ExecutablePath,
    IReadOnlyList<string> Arguments,
    IReadOnlyDictionary<string, string> EnvironmentVariables);

// 3. 注册 nxm:// 协议处理器
public interface IProtocolRegistrar
{
    bool IsRegistered(string scheme);
    void Register(string scheme, string executablePath);
    void Unregister(string scheme);
}

// 4. 目录链接与同卷判断（用于 Phase 2 的文件共享）
public interface IFileSystemLinker
{
    bool AreOnSameVolume(string pathA, string pathB);
    bool TryCreateDirectoryLink(string linkPath, string targetPath);
}
```

**`IGameLauncher` 是这个设计的核心。** Windows 实现返回：

```csharp
new LaunchPlan(
    ExecutablePath: "…/StardewModdingAPI.exe",
    Arguments: ["--mods-path", profileAbsoluteModsPath],
    EnvironmentVariables: new Dictionary<string, string>());
```

未来 Linux 实现返回空参数 + `SMAPI_MODS_PATH` 环境变量即可，**上层用例代码一行都不用改**。

Windows 上的具体实现要点：

- Steam 版：解析 `libraryfolders.vdf` 遍历全部库目录，校验 `steamapps/common/Stardew Valley/Stardew Valley.dll` 存在
- GOG 版：读注册表 `HKLM\SOFTWARE\WOW6432Node\GOG.com\Games\<id>\path`
- 手动指定：设置页允许直接选目录，优先级最高
- Xbox / Game Pass 版：SMAPI 官方不支持，探测到后明确提示并退出引导

`IProtocolRegistrar` 的 Windows 实现直接写 `HKCU\Software\Classes\nxm`，不需要管理员权限。其他平台可分别用 `xdg-mime` 或 macOS 的 `LSSetDefaultHandlerForURLScheme`，接口已经留好。

### ADR-005：启用 / 禁用的实现方式

**决策。** 禁用 = 把模组目录从 Profile 的 `Mods` 移到同级的 `_disabled` 目录；启用 = 移回。不使用重命名后缀的方案。

**理由。** 移动到 `Mods` 之外是唯一不依赖 SMAPI 内部扫描规则的做法。若依赖"SMAPI 会跳过某种命名"，就变成对未文档化行为的依赖，SMAPI 小版本更新就可能失效。移动目录的语义清晰、可逆、不改变目录内容。

**代价。** 同一卷内移动是元数据操作，几百个模组也是毫秒级，无性能问题。跨 Profile 引用硬链接时，移动链接不破坏源文件，行为依然正确。

### ADR-006：SMAPI 升级策略

**决策。** SMAPI 升级是一次带预检、带快照、可回滚的事务，而不是"下载安装器跑一下"。

流程：

```
1. 预检
   ├─ 读当前 SMAPI 版本、游戏版本
   ├─ 从 GitHub Releases API 取最新版（无需 Token，注意限流）
   ├─ 若最新版为预发布、当前为稳定版 → 默认不推荐，需显式勾选
   └─ 扫描全部 Profile 的 manifest，找出 MinimumApiVersion 高于新版本的模组
2. 冲突提示
   ├─ 列出将被"新 SMAPI 版本不足以满足"的模组
   ├─ 列出 smapi.io 标记 brokeIn 覆盖该版本的模组
   └─ 用户确认后继续，或取消
3. 快照
   ├─ 归档 SMAPI 相关文件（StardewModdingAPI.exe、smapi-internal/、Stardew Valley.deps.json 等）
   └─ 归档全部 Profile 的 Mods 清单（不复制文件，只记录指向 library 的引用）
4. 执行
   ├─ 下载 SMAPI-x.y.z-installer.zip 并校验
   ├─ 解压到临时目录
   └─ 调用 installer：--install --game-path "<root>" --no-prompt
5. 校验与提交
   ├─ 检查退出码、检查 StardewModdingAPI.exe 的版本信息是否为新版本
   ├─ 成功 → 记录到操作历史，清理临时目录
   └─ 失败 → 自动回滚到快照，向用户报告具体失败阶段
```

**回滚能力必须有。** SMAPI 大版本升级（如 3.x → 4.0）历史上导致过大量模组失效，这正是用户最怕的场景。只做"升级"不做"回退"的管理器，等于把风险原样转移给用户。

### ADR-007：界面文案用 JSON 资源，支持运行时热切换

**决策。** 文案存放在 `Assets/i18n/{locale}.json`，由 `index.json` 登记可用语言。启动时读取并注入 `Application.Resources`，界面通过 `DynamicResource` 引用。

**理由。**

1. 社区补充语言只需新增一个 JSON 并在 `index.json` 登记，**不需要编译、不需要改代码**。这直接服务于"开源后由其他开发者适配"的目标；若用 `.resx` 强类型资源，"加一门语言"就变成一次代码变更，门槛陡增
2. `DynamicResource` 让语言切换即时生效，无需重启
3. 缺失的键回退到英文，不会出现整片空白

**约束。**

- 增删键时必须同步所有语言文件。当前用脚本比对键集合，P2 起纳入单元测试强制校验
- 不引入 XAML 强类型资源，理由见第 1 点

### ADR-008：界面布局参考 MAA

**决策。** 采用 MAA（MaaAssistantArknights）的组织方式：左侧 62px 图标窄栏承担全局导航，配置类内容统一收进设置页，主区域完整让给模组列表。

**理由。**

1. 模组管理器的核心场景是浏览与批量操作几百个模组，纵向空间是稀缺资源。把游戏路径、版本号这类信息放在首屏，等于用最贵的位置放最不需要频繁看的内容
2. 设置项采用"左侧标题 + 说明、右侧控件"的行式布局，扫读成本低，视觉干扰小
3. 游戏目录、界面语言都是一次配置长期不动的项，放进设置页比放在主界面合理

**约束。**

- 图标栏只放全局导航，不放页面内操作；页面级操作固定在内容区右上角
- 导航项控制在 5 个以内，超出则需要分组
- 主区域不得再挤入配置项

### ADR-009：启动是「方式 × 配置档」两个维度

**决策。** 启动不是二选一，而是两个独立维度自由组合：**方式**（SMAPI / 原版）× **配置档**（任意已保存的模组集合）。

`IGameLauncher.BuildLaunchPlan(game, profile, mode)` 按组合产出三种计划：

| 方式 | 配置档 | 可执行文件 | 参数 |
|---|---|---|---|
| 原版 | 不参与 | `Stardew Valley.exe` | 无 |
| SMAPI | 默认档 | `StardewModdingAPI.exe` | 无（等价于默认 Mods） |
| SMAPI | 自建档 | `StardewModdingAPI.exe` | `--mods-path "<profile.ModsPath>"` |

**理由。**

1. 玩家真实的需求是"这次想玩哪一套模组"，而不是"要不要模组"。把两者压成一个下拉，会让"周一用轻量套装联机、周末用完整套装单人"这类场景无解
2. 原版启动有独立价值：出问题时用它做对照，能立刻判断是游戏本身的问题还是模组的问题。这是排查的第一步，不该被省掉
3. 默认档刻意省略 `--mods-path`，让 SMMS 启动与手动双击 SMAPI 的行为完全一致，减少"管理器改了行为"这类难查的差异

**约束。**

- 原版模式下配置档选择器禁用，读取它没有意义
- 切换配置档会同步改变模组页的扫描目标。若只改启动参数而不改列表，就会出现"列表显示 A 套、启动却用 B 套"的错觉
- 只跟踪本进程启动的游戏实例。玩家自行从 Steam 启动的进程不可见——扫系统进程既慢又容易误判

## 7. 部署方案

### 7.1 分发产物

使用 Velopack，一次构建产出三种产物，全部托管在 GitHub Releases，无需自建服务器：

| 产物 | 用途 | 大小估算 |
|---|---|---|
| `SMMS-win-Setup.exe` | 标准安装包，注册 `nxm://` 协议，带自动更新 | 约 30–40 MB |
| `SMMS-win-Portable.zip` | 绿色便携版，解压即用 | 约 30–40 MB |
| `*-delta.nupkg` | 增量更新包，仅传输差异部分 | 通常 1–5 MB |

### 7.2 打包配置

```
dotnet publish src/SMMS.Desktop -c Release -r win-x64 --self-contained true ^
  -p:PublishReadyToRun=true -p:PublishSingleFile=false
vpk pack --packId SMMS --packVersion <ver> --packDir <publish输出> --mainExe SMMS.Desktop.exe
```

**为什么自包含而不是框架依赖。** 目标用户是普通玩家，不能假设机器上装了 .NET 10 桌面运行时。自包含解压后约 70–120 MB，压缩后 30–40 MB，这个代价换"双击就能用"是值得的。团队内部开发仍可用框架依赖模式，构建更快。

**不使用单文件发布。** Velopack 需要按目录结构做增量比对，单文件会把整个 exe 视为一个变化单元，delta 更新失效。

**体积优化项（后续可做）。** 开启 `PublishTrimmed` 配合 Avalonia 的 trimming 配置，预计可压到 45–60 MB。但 trimming 对反射有风险，需在功能稳定后单独验证一轮，不作为首个版本的目标。

### 7.3 自动更新

Velopack 内置更新流程：启动时检查 GitHub Releases 的 latest 清单，发现新版本后台下载 delta 包，下次启动应用。用户侧只需在设置里提供"检查更新"入口与更新通道选择（稳定 / 预览）。

### 7.4 nxm:// 协议注册时机

- 便携版：首次启动时询问是否注册，写入 `HKCU`（当前用户，无需管理员），卸载/删除目录前可一键注销
- 安装版：安装过程中注册，卸载时清理

两种方式都只写 `HKCU\Software\Classes`，不触发 UAC。

## 9. 待验证事项

以下事项不影响架构决策，但实施时必须先用真机验证，避免建立在猜测上。

1. ~~SMAPI 版本读取方式~~ ✅ 已验证：`FileVersionInfo.ProductVersion` 返回 `4.5.1+da2219…`，用 `\d+(\.\d+){1,3}` 提取首段即可
2. ~~游戏版本读取方式~~ ✅ 已验证：`ProductVersion` 返回 `1.6.15, , 24356, `，同一正则取首个匹配得到 `1.6.15`
3. **smapi.io 的批量上限与速率限制**：文档未明确单次可提交的模组数上限，需实测确定分批大小（初步按 100 个一批）
4. **GitHub Releases API 匿名限流**：每小时 60 次，需做本地缓存，避免频繁请求
5. **SMAPI 安装器在游戏运行中调用的行为**：需确认是否会静默失败，还是明确报错（影响升级前的进程检测逻辑）
6. **Nexus OAuth2 的 token 刷新边界**：access token 有效期约 6 小时，需处理后台长时间挂起后的刷新
7. **`nxm://` 回调在浏览器中的并发行为**：用户连点多个下载时，SMMS 需要队列化处理而不是并发冲突
